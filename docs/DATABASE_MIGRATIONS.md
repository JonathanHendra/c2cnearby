# Database Migrations & Associations Policy

## 1. Absolute rules

1. **No automatic schema synchronization.** `sequelize.sync()`, `sync({ alter })`,
   `sync({ force })`, model-driven table creation and association-driven FK creation are
   forbidden in all code paths (including tests that touch a real database).
2. Every table, column, index, foreign key, enum change, and constraint is introduced by a
   migration with `up()` and `down()`.
3. Models describe existing tables only. They set `tableName`, `underscored`, and explicit
   column definitions; they never define associations.
4. Associations live only in `backend/src/database/associations.ts`, registered exactly once via
   `initializeAssociations(models)` after all models are registered.
5. Applied migrations are immutable. Any correction is a **new** migration.
6. The server refuses to become ready when the database does not match the expected migration
   set.

## 2. Migration tooling

- Migration runner: `umzug` driven by `backend/src/database/migration-runner.ts`, using the same
  Sequelize connection as the app.
- Migration files: `backend/src/database/migrations/NNNN-descriptive-name.ts` with a numeric
  ordering prefix and a timestamp inside the descriptive name when generated by Sequelize CLI
  (`20261105T010000-create-users.ts`). Both formats are supported by the runner; the repository
  uses Sequelize-CLI-compatible timestamps for auditability.
- Storage table: `SequelizeMeta` (default) with the migration filename as primary key.
- Each migration exports `up({ context: queryInterface, Sequelize })` and
  `down({ context: queryInterface, Sequelize })`.

### npm scripts

```bash
npm run db:migrate          # apply pending migrations
npm run db:migrate:status   # list applied/pending
npm run db:migrate:undo     # roll back the most recent migration
npm run db:migrate:undo:all # development only
npm run db:seed             # run seeders (idempotent)
npm run db:seed:undo        # undo seeders
```

`db:migrate` is **never** invoked automatically by `server.ts`. Production runs it as an explicit
deployment step after a verified backup.

## 3. Naming and structure

- File: `20261105010100-create-users.ts`
- Table names: plural snake_case (`users`, `user_locations`, `price_offers`).
- Constraint names are explicit and stable:
  - `fk_listings_user_id` / `fk_listings_category_id`
  - `uq_users_firebase_uid`
  - `idx_listings_feed`
  - `chk_price_offers_positive`
- One domain per migration where possible; a large domain may be split by concern
  (tables → indexes → constraints) but never left half-applied without a working `down()`.

## 4. Migration authoring checklist

- [ ] Table/column exists only because a product requirement needs it.
- [ ] Types: `CHAR(36)` UUIDs, `DECIMAL(15,2)` money, `DATETIME(3)` timestamps, `POINT SRID 4326`.
- [ ] `ON DELETE` / `ON UPDATE` chosen deliberately.
- [ ] Indexes match documented query patterns (see `DATABASE.md` §3).
- [ ] `down()` reverses exactly what `up()` did and does not destroy unrelated data.
- [ ] Destructive change? Requires explicit approval, backup, and expand-and-contract.
- [ ] Tested with `db:migrate` then `db:migrate:undo` on a scratch database.

## 5. Safe evolution (expand → migrate → contract)

For risky changes (rename, type change, NOT NULL introduction):

1. **Expand**: add nullable column / new table / dual-write path.
2. **Backfill**: batched, resumable, idempotent job or SQL script; throttled to protect
   production.
3. **Migrate reads/writes** to the new structure and deploy.
4. **Contract**: drop the old column/table in a later release, after confirming no reader
   depends on it.
5. Never combine a destructive step with the release that stops using the old structure.

Prohibited shortcuts: editing an applied migration, dropping a column without checking deployed
code, `ALTER TABLE ... MODIFY` on a large table during peak traffic without a plan, or relying on
`sync({ alter: true })` to "fix" drift.

## 6. Readiness and drift detection

`checkMigrationStatus()` in `migration-runner.ts`:

- Executes Umzug `pending()`.
- If any migration is pending → readiness fails with `DB_MIGRATIONS_PENDING` and the list of
  filenames. The process can still serve `/healthz` but `/readyz` returns 503.
- Logs the latest applied migration name and count.
- Optionally compares a hash manifest of migration filenames in production to detect modified
  historical files (deploy-time check).

## 7. Backup and restore

- Production: daily `mysqldump --single-transaction --routines --triggers --events` plus binary
  logs for point-in-time recovery; encrypted off-host copy with 30-day retention.
- Verify restore monthly on a scratch instance; record the drill in the ops log.
- Before any risky migration: on-demand dump and explicit confirmation that the dump is readable.
- Rollback strategy: prefer a new forward migration (`down()` is for development and emergencies);
  restore from backup only for data-loss incidents.

## 8. Manual associations

`initializeAssociations()` is called once from `database/index.ts`. Each association sets
`constraints: false` so Sequelize never emits DDL. Aliases are stable API surface for includes;
see `docs/DATABASE_ASSOCIATIONS.md` for the full alias table.

Adding a relation requires:

1. A migration that adds the FK column and constraint (if not present).
2. A model attribute for the FK.
3. An entry in `associations.ts` (both directions).
4. A model/association test: all models initialize, all associations resolve, and no schema
   query is emitted during initialization.

## 9. Seeders

- Development/staging only unless explicitly approved for production (categories, admin roles).
- Idempotent: upsert by natural key (`slug`, `firebase_uid`).
- Seed data must not contain real phone numbers, addresses or personal data.
- Demo listings use approximate coordinates around a public landmark, never a home address.
